## Core Rules

1. Never push directly to main.
2. Never make large rewrites unless the task requires it.
3. Never change Vercel production settings without approval.

## Generated files — do not read them as truth

`public/sitemap.xml`, `vercel.json` and `public/_redirects` are **build outputs**, regenerated by
`prebuild` (`scripts/generate-sitemap.ts`, `scripts/generate-redirects.ts`). They are committed to
git, so the copy in the repo is routinely **days out of date** relative to its source.

* **Never hand-edit them.** The next `prebuild` reverts the change. This has happened repeatedly —
  see decisions D-020 and D-022 in `seo-department/operations/SEO-DECISION-LOG.md`.
* **Never conclude a URL is missing from the sitemap by reading `public/sitemap.xml`.** On
  2026-08-05 an SEO audit did exactly that and produced three false "CRITICAL" findings, claiming
  the `/private-chef-bali` pillar and the whole B2B cluster were unsubmitted. Live production
  contained all of them.
* To check what is actually live, fetch `https://mychef.id/sitemap.xml`. To check intent, read the
  real source: `src/data/sitemap.ts` — note it builds ~240 entries via `buildSitemap()` from twelve
  imported sources, so `grep -c "path:"` on that file returns a meaningless number.
* `scripts/verify-all.ts` now fails the build if a static route in `App.tsx` is neither in the
  sitemap, in `NOINDEX_PATHS`, nor a redirect source. Keep `NOINDEX_PATHS` in
  `scripts/generate-sitemap.ts` in sync with `noindexFollowPaths` in `scripts/inject-meta.ts` —
  a URL that is `noindex` must never appear in the sitemap.

## Work Process for Every Task

**Step 1: Read project context**
Inspect:
* `AI_MAP.md`
* package.json
* framework config
* routing structure (`src/App.tsx`, `src/data/sitemap.ts`)
* environment variable usage
* relevant files
* previous errors if available

**Step 2: Read approved skills**
Read every relevant file inside `/ai-skills` before editing.

**Step 3: Diagnose**
Explain:
* what is wrong
* why it is likely wrong
* which files matter
* what can break if changed incorrectly

**Step 4: Plan**
Give a minimal fix plan:
* files to change
* files not to touch
* expected result
* risk level

**Step 5: Edit**
Make the smallest safe change.
Do not mix unrelated tasks.
Do not refactor unless required.

**Step 6: Verify**
Run or instruct these checks:
* npm ci or npm install
* npm run lint if available
* npm run typecheck if available
* npm run build

**Step 7: Vercel safety check**
Confirm:
* production branch not touched directly
* preview deployment should be used first
* changed route works
* main landing pages still work
* forms still work
* metadata still exists
* no environment variables were broken
* no package/config risk remains

**Step 8: Final answer**
Return:

```
Diagnosis:
Files changed:
Risk:
Verification:
Remaining issues:
Final verdict:
```

Final verdict must be one of:
* PASS
* BLOCKED
* NEEDS HUMAN REVIEW

## Agent Swarm Rules

If using multiple agents, assign roles:

* Agent 1: Codebase Mapper — Find relevant files and system structure.
* Agent 2: Error/Debug Specialist — Find build, TypeScript, dependency, import, and runtime risks.
* Agent 3: Vercel Build Reviewer — Check Vercel deployment, build command, env vars, preview risk, and config risk.
* Agent 4: SEO and Routing Protector — Check routes, metadata, sitemap, redirects, internal links, and CTAs.
* Agent 5: Final Reviewer — Decide PASS, BLOCKED, or NEEDS HUMAN REVIEW.

Only the final reviewer may decide PASS, BLOCKED, or NEEDS HUMAN REVIEW.

No agent may push to main.
No agent may change production config.
No agent may ignore failed build output.
No agent may create broad changes outside the task.
